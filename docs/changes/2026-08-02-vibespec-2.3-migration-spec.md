# Migration du bundle VibeSpec Pro vers 2.3.0

**Mode:** standard  
**Status:** verified  
**Owner:** repository maintainers

## Problem

Le dépôt utilise un bundle cloud VibeSpec Pro 2.2.0. Le bundle ne contient pas le nouveau skill de preflight et `cloud check` échoue. La politique de test spécifique au dépôt se trouve à l’intérieur du bloc `AGENTS.md` géré par VibeSpec, ce qui crée un drift et empêche une synchronisation sûre.

## Outcomes

- `OUT-001`: `vibespec cloud check . --json` réussit avec un bundle 2.3.0 sans finding.
- `OUT-002`: la politique `## 10. Discipline de test` reste présente hors du bloc géré avec le même contenu et le même hash SHA-256.
- `OUT-003`: les workflows applicatifs continuent de passer sans changement du comportement produit.

## Functional requirements

- `REQ-001`: Déplacer la politique `## 10. Discipline de test` immédiatement avant `<!-- BEGIN VIBESPEC CLOUD -->`, sans modifier son contenu.
- `REQ-002`: Synchroniser le bundle cloud depuis la source officielle locale 2.3.0 pour les agents `codex` et `claude`, sans utiliser `--force`.
- `REQ-003`: Installer les skills `vibespec-preflight` pour les deux agents et mettre à jour le lock vers 2.3.0.
- `REQ-004`: Préserver `.vibespec/project.yaml`, les profils `web-app` et `backend-api`, ainsi que toutes les instructions du dépôt hors bloc géré.
- `REQ-005`: Ajouter le dépôt au registre global VibeSpec après validation.

## Non-functional requirements

- `NFR-001`: Le hash SHA-256 du bloc de politique avant et après déplacement doit rester `1cb68d59d6db351721d9b351e97a38d4e1506d61a3cb24c9fd8896d496ea6459` sur 1731 octets UTF-8.
- `NFR-002`: La migration doit produire zéro finding dans `cloud check` et zéro changement restant dans `cloud diff`.
- `NFR-003`: Les commandes `npm run lint`, `npm run typecheck`, `npm run test` et `npm run build` doivent réussir sur l’état final.

## Invariants and compatibility

- `INV-001`: Aucun `--force`, commit, push, déploiement ou migration de données n’est autorisé.
- `INV-002`: Les sections métier 1 à 9 d’`AGENTS.md` et les instructions hors bloc de `CLAUDE.md` restent inchangées.
- `INV-003`: Aucun contrat API, schéma Prisma, comportement UI, worker, MCP ou dépendance applicative ne change.

## Error and edge-case behavior

- `ERR-001`: Si le bloc géré reste divergent après déplacement, arrêter sans lancer de sync forcé.
- `ERR-002`: Si `cloud sync` refuse la migration ou si une gate échoue, conserver le diff pour diagnostic et ne pas inscrire la migration comme vérifiée.
- `ERR-003`: Si des changements non prévus apparaissent hors des chemins VibeSpec et des artefacts de changement, arrêter la migration.

## Acceptance criteria

- `AC-001` verifies `REQ-001`: la politique est située avant le marqueur BEGIN et son hash/sa taille correspondent à `NFR-001`.
- `AC-002` verifies `REQ-002`: l’historique de commande prouve un sync normal sans `--force`.
- `AC-003` verifies `REQ-003`: le lock indique 2.3.0 et les deux skills preflight sont présents.
- `AC-004` verifies `REQ-004`: la revue du diff ne montre aucun changement métier hors bloc.
- `AC-005` verifies `REQ-005`: `vibespec project show insta-saved-post-explorer --json` retourne une entrée disponible.
- `AC-006` verifies `NFR-002`: `cloud check` réussit et `cloud diff` retourne zéro changement.
- `AC-007` verifies `NFR-003`: les quatre commandes projet réussissent avec des résultats frais.

## Out of scope

- Modifier les règles métier Places ou la politique de test.
- Ajouter Hermes au bundle cloud de ce dépôt.
- Refactorer le produit ou ses tests.
- Committer, pousser, ouvrir une PR ou déployer.

## Assumptions and risks

- `ASM-001`: le bundle 2.3.0 local correspond à la release officielle vérifiée.
- `RSK-001`: une personnalisation dans le bloc géré pourrait être perdue ; mitigation : déplacement préalable, hash et absence de `--force`.
- `RSK-002`: le nouveau bundle peut modifier les instructions d’agents ; mitigation : revue séparée des blocs et `cloud diff` final.
